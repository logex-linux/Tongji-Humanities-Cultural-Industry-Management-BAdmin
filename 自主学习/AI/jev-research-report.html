模型研究报告 · 2026 年 9 月

JEV：一个不生成文字、只返回判断的模型

TypeSafe AI 于 2026 年 9 月 15 日发布的首个「System One 模型」。它不做对话、不写代码、不生成解释， 只把你的数据变成带概率的类型化答案，直接交给代码分支判断。 这份报告的核心问题是：这个主张有多少是真的。

研究对象 Jev（jev-1.13） 发布方 TypeSafe AI 数据截止 2026-09-20 取证来源 25+ 个，经 crawl4ai 抓取

结论先行

Jev 是真实存在的新模型，不是概念或假消息。它于 2026 年 9 月 18 日上线 OpenRouter， 几天内处理超过 1610 亿 token，并已接入 Cloudflare Workers AI 与 LangChain 官方集成。

LLM 生成一段话给你读；Jev 读你的数据，直接返回一个带概率的类型化答案给你的代码用。 官方原话是「把 Jev 当成一个前沿智能的函数调用：非结构化状态进，带类型的概率决策出」。

但需要冷静看待的核心一点：TypeSafe 这次没有发布任何标准基准测试， 性能数字全部来自厂商自建的工作流评测。第三方独立实测结果好坏参半——速度和成本优势得到确认， 判断准确率在有些场景下甚至不如「一行 if 规则」。

01 它是什么

Jev 的 API 只有两个概念：state（要判断的数据，可以是文本或嵌套 JSON）和 questions（关于这些数据的问题）。问题被刻意限制成三种形状， 官方的解释是「形状固定，返回值才永远可解析；选择有限，概率才校准得出来」。

Choice
从你定义的选项里选一个 —— 「这个工单应该归哪个团队？」

返回：选中项 + 每个选项的概率 + 置信度。选项之间是竞争关系，概率和为 1。

Score
沿有顺序的量表打分 —— 「客户有多沮丧？0 = 平静，2 = 非常沮丧」

返回：连续分数 + 底层分布 + 置信度。文档警告不要把小数 Score 当精确测量值。

Noul
判断某个陈述是否为真 —— 「客户是否明确要求回电？」

返回：一个 0–1 的概率，没有单独的置信度字段。

多个问题可以在一次请求里并行评估，同一份 state 只发一遍。官方称加问题几乎不影响响应时间， 也不产生上下文腐烂。一个典型例子是客服工单「payouts 已经失败 3 天」，同时问： 「紧急吗？」→ 0.999、「归谁管？」→ billing（置信度 0.8）、「客户多沮丧？」→ 1.04（置信度 0.94）。

名字来自卡尼曼《思考，快与慢》：System 1 是快速直觉，System 2 是缓慢推理。 TypeSafe 的判断是——被做成产品的是 System 1。

训练方法 RLCD（Reinforcement Learning for Calibrated Decisions）是它最核心的技术主张： 不优化「人类偏好的文本」，而优化「概率真实反映正确率」。这是置信度阈值策略能成立的前提—— 没有校准过的概率，你就写不出 if confidence < 0.5。

官方自己列出的 caveats

速度评测「基本上是在我们西海岸的笔记本上跑的（服务目前部署在那里）」； 定价「我们无法证明这不是补贴，需要长期来证明可持续性」； 速率限制「可能在有新 GPU 交易落地时无预警变化」。

扑克实测 —— 最尖锐的批评 第三方实测

backnotprop.com 的评测是质量最高的独立批评。 作者用 TexasSolver 求解了一个牌面（Q♠9♦4♠，100bb 深，300 次迭代至 0.59% exploitability）， 把底牌、牌面、行动史、底池赔率、SPR 全部在 Python 里算好后喂给 Jev，只问它该采取什么行动。

因为 solver 在 150 个里有 95 个选择过牌，「总是过牌」这条规则就能拿 72%。 在 solver 真正有行动的 55 个牌况里，Jev 的四种方式得 33%–44%，无模型规则 24%–29%。

作者的结论很直白：「Jev 确实在做点什么，但它答错的次数比答对多」， 而且在所有四种方式里，Jev 都会过牌或弃掉 solver 会下注的牌。 另一个反讽案例：Jev 拿着同花听牌面对已成型的同花，5 次里有 5 次认为自己领先， 把 89.5 推进 22.5 的底池。

作者同时指出 TypeSafe 跳过了发布标准评测，「我认为这会导致大量天真的部署」。 他还提到一个方法论问题：被展示的用例并没有被分解—— 官方 showcase 是「给模型一个 diff，问它是否安全」、「给一个对话线程，问是否该退款」， 这恰恰是未分解的用法，也正是被卖点的用法；而文档自己要求的是把问题拆成原子判断再在代码里组合。 这两者之间的距离，就是用户实际拿到的效果和演示效果之间的距离。

厂商口径 这一点值得肯定——TypeSafe 有一份 Jev 1.13 jaggedness 页面 （2026-09-17 复核），开头就是「Jev isn't perfect」。

jev-1.13 已知失败模式，来源：docs.typesafe.ai/model-jaggedness/jev-1.13
#失败模式应该怎么做
1字面阅读（过于 literal）写出精确条件，为每个选项写清标准
2数学与数字，需要数值精度把算术留在代码里

文档明确说：「jev-1.13 快、校准、擅长常识判断，但不完美。 它在 System One 任务上表现最好，可能需要额外间接层级的任务上会吃力。它能相当字面地理解。」

06 怎么评价这个模型

它真正解决的问题是真实的

任何做过生产级分类、路由的人都会认出这几个痛点：LLM 返回的 JSON 套在 markdown 代码块里要剥； 拼错的 "techincal" 静默写进数据库；为一个 0–2 的分数生成 372 个 token 的解释 （你在为「它向你解释自己」付费）；自报的 confidence 字段从未和真实结果对齐过。 Jev 的设计直击这些。

而且「零幻觉」这个口号在它的语境下是成立的——输出永远是预期结构，模型不可能产生类型错误， 官方称这在数学上可证，只需一个反例就能证伪。

但「系统一模型」这个品类叙事要小心

批评者的观察很到位：被展示的用例并没有被分解。官方 showcase 是「给一个 diff 问是否安全」、 「给一个对话线程问是否该退款」——这恰恰是未分解的用法，也正是被卖点的用法。 而文档自己要求的是把问题拆成原子判断再在代码里组合。

从工程实践看，值得记住的几条：多个标签可能同时成立时用多个 Noul， 不要用一个 Choice（Choice 的概率互相竞争，会此消彼长）； confidence < 0.5 是兜底，往上每个动作按后果分设阈值—— 查余额这种只读操作不用门槛，批准转账这种不可逆操作要； 阈值本身没有标准答案，必须拿你自己的数据跑出来。

对你是否有用，取决于一个问题

你的场景是不是「每封邮件、每个工单、每次工具调用都要判断一次」的高频结构化决策？ 如果是，成本结构确实让「全量判断」在经济学上首次成立—— $0.042/百万输入 token，一美分约 240 次单问题决策。

如果只是偶发的判断，一个普通 LLM 加 structured output 就够了—— 而且 mini-Jev 的实验说明这条路你能自己在冻结模型上拿到大部分收益。

最实用的建议，来自扑克评测作者

你必须对每一个想交给它的场景，逐个对着你信任的答案键做评估， 并算清在那里一次错误判断的代价。不要相信任何聚合分数——包括本报告列出的这些。

07 局限与未解问题

  • 无同行评审 未能验证
    arXiv 上搜不到 RLCD 或 System One 相关论文（检索 all:"RLCD" AND all:"calibrated" 返回 0 条结果）。训练方法只有博客描述。
  • 无标准基准 未能验证
    厂商明确选择自建「工作流评测」，参考答案是 Astra 和 Fable 这两个最贵最大模型的平均预测。 这比刷榜诚实，但也意味着没有一个数字能告诉你 Jev 是否跨过了你要交给它的那个决策的门槛。 官方原话：「这也意味着，没有任何数字能告诉你，对于你即将交给它的那个决策，Jev 是否达标。」
  • 校准性无独立验证 未能验证
    这是它全部价值主张的地基。我没有找到任何针对 jev-1.13 的独立校准曲线测量。 mini-Jev 明确警告它自己的分数「不是校准概率」。
  • 定价可持续性存疑 —— 官方自己承认「我们无法证明这不是补贴」。
  • 延迟基准的采样环境 —— 官方称在自己的笔记本上跑，服务部署在美国西海岸， 其他地区实际延迟可能不同。OpenRouter 侧实测 P50 为 0.28s。
  • 速率限制动态调整中 —— 官方称「需求非常大，限制可能在有新 GPU 交易落地时无预警变化」。
  • 一篇中文批评文章未能取得全文 —— 知乎《万字长文解读 Jev 模型》被反爬拦截（HTTP 403）， 仅从搜索摘要确认其持批评立场（「没有超越统计学的理论创新，能力边界也很窄」），未作为论据采用。
