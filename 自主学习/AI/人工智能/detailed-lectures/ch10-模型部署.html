10.2 Docker——打包你的模型

为什么用 Docker？

"在我机器上能跑" → 用 Docker 把整个环境（Python版本、库、模型文件）打包成一个镜像，哪里都能跑。

Dockerfile 示例

# Dockerfile
FROM python:3.11-slim

WORKDIR /app

# 安装依赖
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 复制代码和模型
COPY . .

# 暴露端口
EXPOSE 8000

# 启动命令
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
# 构建和运行
docker build -t my-ai-app .
docker run -p 8000:8000 my-ai-app

# 现在访问 http://localhost:8000 就能用了！
📌 Docker 核心概念
  • 镜像 (Image)：打包好的环境模板（只读）
  • 容器 (Container)：镜像的运行实例
  • Dockerfile：描述如何构建镜像的脚本
  • docker-compose：同时运行多个服务（API + 数据库 + 向量库）

10.3 FastAPI——把模型变成 API

"""main.py - 生产级模型服务"""
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
import torch
import time

app = FastAPI(title="AI Model Service")

# 模型加载（启动时一次性加载）
class ModelService:
    def __init__(self):
        self.model = None
    
    def load(self):
        # 加载你的模型
        self.model = torch.load("model.pt")
        self.model.eval()

service = ModelService()

@app.on_event("startup")
def startup():
    service.load()

# 请求/响应格式
class PredictRequest(BaseModel):
    text: str

class PredictResponse(BaseModel):
    result: str
    confidence: float
    latency_ms: float

@app.post("/predict", response_model=PredictResponse)
def predict(req: PredictRequest):
    start = time.time()
    
    # 推理
    result, confidence = run_inference(service.model, req.text)
    
    latency = (time.time() - start) * 1000
    return PredictResponse(
        result=result,
        confidence=confidence,
        latency_ms=round(latency, 2)
    )

@app.get("/health")
def health():
    return {"status": "ok", "model_loaded": service.model is not None}
# 运行

# uvicorn main:app --reload

10.4 模型优化——量化与加速

问题：模型太大、推理太慢

一个 7B 参数的模型，FP32 精度下占 ~28GB 显存。普通 GPU 装不下！

量化：减少每个参数的位数

精度每参数位数7B模型大小质量损失
FP3232 bit~28 GB无
FP1616 bit~14 GB极小
INT88 bit~7 GB很小
INT44 bit~3.5 GB轻微
📌 量化的直觉

原来每个参数用 32 位浮点数存储（如 0.123456789）。

量化后只用 4 位整数（如 3），精度降低但体积减少 8 倍。

类比：把高清照片压缩成缩略图——细节少了，但主要内容还在。

# 用 bitsandbytes 做 4-bit 量化加载
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

config = BitsAndBytesConfig(load_in_4bit=True)
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.1-8B",
    quantization_config=config
)
# 原来需要 ~16GB 显存，现在只需要 ~5GB！

# 安装

    --model Qwen/Qwen2.5-7B-Instruct \
    --port 8000

# 核心优化：PagedAttention
# 像操作系统管理内存页一样管理 KV Cache
# 吞吐量比原生 HuggingFace 提升 2-4x
工具适用场景特点

vLLM生产部署、高并发最高吞吐量

10.6 监控——模型会"退化"

数据漂移

模型训练时的数据分布和上线后的数据分布可能不同。比如：

  • 训练数据：2023年的用户评论
  • 线上数据：2026年的用户评论（新词汇、新话题）

模型性能会悄悄下降，但不会报错！

需要监控什么？

指标含义告警阈值
推理延迟 (P99)99% 请求的响应时间> 500ms
预测置信度模型输出的概率平均 < 0.7
用户反馈点赞/点踩比例差评 > 15%
输入分布输入数据是否变化KS 检验 p < 0.05

10.7 实验管理——追踪你的训练

# 用 Weights & Biases 记录实验
import wandb

wandb.init(
    project="my-project",
    config={
        "model": "bert-base",
        "lr": 3e-5,
        "batch_size": 32,
        "epochs": 5,
    }
)

for epoch in range(5):
    train_loss = train_one_epoch()
    val_acc = evaluate()
    
    wandb.log({
        "train/loss": train_loss,
        "val/accuracy": val_acc,
        "epoch": epoch,
    })

wandb.finish()
# 在 wandb.ai 面板上可以看到所有实验的对比图
📌 实验管理要记录什么？
  • 超参数：学习率、batch size、模型结构...
  • 指标：训练损失、验证准确率（每个 epoch）
  • 模型文件：最佳 checkpoint
  • 数据版本：用了哪个版本的数据集
  • 环境：GPU 型号、库版本

10.8 完整部署实战

✏️ 例题 10.1：部署一个情感分析 API
# 项目结构
# my-app/
# ├── Dockerfile
# ├── requirements.txt
# ├── main.py          ← FastAPI 服务
# └── model/           ← 模型文件

# requirements.txt
# fastapi==0.104.0
# uvicorn==0.24.0
# transformers==4.36.0
# torch==2.1.0

# main.py
from fastapi import FastAPI
from transformers import pipeline

app = FastAPI()
classifier = pipeline("sentiment-analysis", 
                      model="uer/roberta-base-finetuned-chinanews-chinese")

@app.post("/analyze")
def analyze(text: str):
    result = classifier(text)[0]
    return {
        "text": text,
        "label": result["label"],
        "score": round(result["score"], 4)
    }

# 部署步骤：
# 1. docker build -t sentiment-api .
# 2. docker run -p 8000:8000 sentiment-api
# 3. 访问 http://localhost:8000/docs 查看 API 文档
# 4. POST /analyze {"text": "这个产品太棒了！"}
⚠️ 常见误区
✗ "模型训练好就完事了"
✓ 上线只是开始。数据分布会随时间变化（数据漂移），模型性能会悄悄下降。需要持续监控、定期重训练。
✗ "量化会严重损害模型质量"
✓ INT4 量化通常只损失 1-2% 精度。对大多数应用完全可接受，但模型体积缩小 8 倍、推理速度提升 2-3 倍。性价比极高。
✗ "Docker 只是给运维用的"
✓ AI 工程师必须掌握基本的容器化。"在我机器上能跑"是生产事故的头号原因。Docker 确保环境一致性，是模型上线的基本功。

10.9 本章习题

📝 概念理解题
  1. 为什么不能直接把 Notebook 代码部署到生产环境？（说出 2 个原因）
  2. Docker 解决了什么问题？
  3. 模型量化 INT4 相比 FP32，体积减少多少倍？质量损失大吗？
  4. 什么是数据漂移？为什么需要监控？
  5. vLLM 比直接用 HuggingFace 推理快在哪里？
参考答案
  1. ① 环境依赖不一致（"在我机器上能跑"）；② 没有错误处理、日志、并发支持
  2. 把整个运行环境（OS、Python、库、模型）打包成镜像，任何机器都能一致运行。
  3. 32/4 = 8 倍。质量损失通常很轻微（< 2% 准确率下降），大多数场景可接受。
  4. 线上数据分布和训练时不同（如新词汇、新话题），导致模型性能悄悄下降。监控能及时发现并触发重训练。
  5. PagedAttention：像 OS 管理内存页一样管理 KV Cache，减少显存碎片，提高吞吐量 2-4x。
📝 实践题
  1. 写一个 Dockerfile，把第9章的 RAG 系统打包成 Docker 镜像并运行。
  2. 用 FastAPI 写一个 /predict 接口，加载一个 HuggingFace 模型，返回分类结果和置信度。
  3. 用 Ollama 在本地运行一个 7B 模型，用 Python 调用它的 API 完成一个对话。
  4. 挑战：用 docker-compose 编排：FastAPI 服务 + Chroma 向量数据库 + Redis 缓存，实现一个完整的 RAG 应用。
